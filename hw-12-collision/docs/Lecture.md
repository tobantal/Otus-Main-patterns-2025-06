## 1. Введение в паттерн

### 1.1 Определение

**Цепочка обязанностей (Chain of Responsibility, CoR)** — поведенческий паттерн проектирования, который позволяет избежать жёсткой привязки отправителя запроса к его получателю, давая возможность обработать запрос нескольким объектам.

Паттерн связывает объекты-получатели в цепочку и передаёт запрос вдоль этой цепочки, пока его не обработают.

### 1.2 Проблема

Рассмотрим типичные ситуации:
- Есть множество типов сообщений и множество обработчиков
- Заранее неизвестно, какой обработчик должен обработать конкретный запрос
- Набор обработчиков должен изменяться динамически

**Пример**: Контекстно-зависимая справка в GUI. При нажатии F1 над кнопкой — нужно показать справку для кнопки, если её нет — для панели, если и её нет — для окна.

### 1.3 Решение

Паттерн предлагает:
1. Превратить обработчики в объекты
2. Связать их в цепочку
3. Каждый обработчик либо обрабатывает запрос, либо передаёт следующему

```
[Запрос] → [Handler1] → [Handler2] → [Handler3] → [Результат]
                ↓            ↓            ↓
            [Обработка]  [Обработка]  [Обработка]
```

## 2. Структура паттерна

### 2.1 Диаграмма классов (C++)

```
┌─────────────────────────────────────────┐
│              IHandler                   │
├─────────────────────────────────────────┤
│ + setNext(handler: IHandler*): void     │
│ + handle(request: Context&): void       │
└─────────────────────────────────────────┘
                    △
                    │
        ┌───────────┴───────────┐
        │                       │
┌───────────────┐       ┌───────────────┐
│  BaseHandler  │       │ ConcreteHandler│
├───────────────┤       ├───────────────┤
│ - next_       │       │ + handle()    │
├───────────────┤       └───────────────┘
│ + setNext()   │
│ + handle()    │
└───────────────┘
```

### 2.2 Реализация на C++

```cpp
/**
 * @brief Интерфейс обработчика в цепочке
 */
class IHandler {
public:
    virtual ~IHandler() = default;
    
    /**
     * @brief Установить следующий обработчик в цепочке
     * @param handler Указатель на следующий обработчик
     * @return Указатель на следующий обработчик (для цепочки вызовов)
     */
    virtual IHandler* setNext(std::shared_ptr<IHandler> handler) = 0;
    
    /**
     * @brief Обработать запрос
     * @param context Контекст обработки
     */
    virtual void handle(Context& context) = 0;
};

/**
 * @brief Базовый класс обработчика с реализацией цепочки
 */
class BaseHandler : public IHandler {
protected:
    std::shared_ptr<IHandler> next_;
    
public:
    IHandler* setNext(std::shared_ptr<IHandler> handler) override {
        next_ = handler;
        return handler.get();
    }
    
    void handle(Context& context) override {
        if (next_) {
            next_->handle(context);
        }
    }
};
```

## 3. Варианты поведения обработчика

### 3.1 Классический вариант: "Обработай или передай"

Обработчик пытается обработать запрос. Если не может — передаёт следующему:

```cpp
void handle(Context& context) override {
    if (canHandle(context)) {
        doHandle(context);
    } else if (next_) {
        next_->handle(context);
    }
}
```

### 3.2 Валидация: "Проверь и передай"

Обработчик проверяет допустимость запроса. Если недопустим — выбрасывает исключение:

```cpp
void handle(Context& context) override {
    if (!isValid(context)) {
        throw ValidationException("Invalid request");
    }
    if (next_) {
        next_->handle(context);
    }
}
```

### 3.3 Обогащение: "Дополни и передай"

Обработчик добавляет данные в контекст и передаёт дальше:

```cpp
void handle(Context& context) override {
    // Добавляем данные
    context.userData = extractUserFromToken(context.authHeader);
    
    if (next_) {
        next_->handle(context);
    }
}
```

### 3.4 Конвейер: "Выполни свою часть"

Каждый обработчик выполняет свою часть работы, запрос "проезжает" через всех:

```cpp
void handle(Context& context) override {
    // Выполняем свою часть работы
    doMyPart(context);
    
    // Всегда передаём дальше
    if (next_) {
        next_->handle(context);
    }
}
```

## 4. Применение к проверке коллизий

### 4.1 Проблема эффективного перебора

При наивном подходе проверки коллизий между N объектами требуется O(N²) проверок. Для 1000 объектов это ~500000 проверок каждый кадр!

### 4.2 Решение: Пространственное разбиение

Разбиваем игровое поле на **окрестности (регионы)**:
- Объекты в разных регионах не могут столкнуться
- Проверяем коллизии только между объектами одного региона

```
┌─────────┬─────────┬─────────┐
│ (0,0)   │ (1,0)   │ (2,0)   │
│  ●  ●   │    ●    │         │
├─────────┼─────────┼─────────┤
│ (0,1)   │ (1,1)   │ (2,1)   │
│    ●    │  ● ● ●  │   ●     │
├─────────┼─────────┼─────────┤
│ (0,2)   │ (1,2)   │ (2,2)   │
│         │   ●     │  ●  ●   │
└─────────┴─────────┴─────────┘
```

### 4.3 Проблема границ

Объекты около границы региона могут столкнуться с объектами в соседнем регионе:

```
┌─────────┬─────────┐
│         │         │
│      ●→ │ ←●      │   ← Эти объекты могут столкнуться!
│         │         │
└─────────┴─────────┘
```

### 4.4 Решение: Несколько систем окрестностей

Используем **две (или более) системы окрестностей со смещением**:

```
Система 1:                    Система 2 (смещена на полрегиона):
┌─────┬─────┐                 ┌─────┬─────┐
│  ●  │  ●  │                 │     │●  ● │
│     │     │                 │     │     │
└─────┴─────┘                 └─────┴─────┘
  Граница!                      Один регион!
```

Таким образом, объекты на границе одной системы окажутся в одном регионе другой системы.

## 5. Архитектура решения

### 5.1 Ключевые компоненты

```
┌─────────────────────────────────────────────────────────────┐
│                    ICollisionChecker                        │
│  (интерфейс проверки коллизий - не реализуем)               │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                    IRegionResolver                          │
│  + getRegion(object): RegionId                              │
│  (определяет регион для объекта по его позиции)             │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                    RegionManager                            │
│  + addObject(object): void                                  │
│  + removeObject(object): void                               │
│  + getObjectsInRegion(regionId): vector<IGameObject*>       │
│  (управляет объектами в регионах одной системы)             │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                 UpdateRegionCommand : ICommand              │
│  - определяет текущую окрестность объекта                   │
│  - если изменилась: удаляет из старой, добавляет в новую    │
│  - создаёт команды проверки коллизий в макрокоманду         │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│              MultiRegionCollisionSystem                     │
│  - содержит несколько RegionManager со смещением            │
│  - координирует проверку коллизий во всех системах          │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 Диаграмма классов

```
                        ICommand
                            △
                            │
            ┌───────────────┼───────────────┐
            │               │               │
   UpdateRegionCommand  CheckCollision  MacroCommand
                         Command            │
                                           contains
                                            │
                                    ┌───────┴───────┐
                                    │               │
                            CheckCollision  CheckCollision
                              Command         Command

IRegionResolver ◇────────── RegionManager ─────────◇ IGameObject*

MultiRegionCollisionSystem ◇────── RegionManager[] (со смещениями)
```

### 5.3 Псевдокод основной логики

```cpp
class UpdateRegionCommand : public ICommand {
private:
    std::shared_ptr<IGameObject> object_;
    RegionManager& regionManager_;
    std::shared_ptr<MacroCommand>& collisionMacro_;  // Ссылка на макрокоманду
    
public:
    void execute() override {
        // 1. Определяем новую окрестность объекта
        RegionId newRegion = regionManager_.getResolver().getRegion(object_);
        
        // 2. Получаем предыдущую окрестность
        RegionId oldRegion = object_->getProperty("currentRegion");
        
        // 3. Если окрестность изменилась
        if (newRegion != oldRegion) {
            // Удаляем из старой
            regionManager_.removeFromRegion(object_, oldRegion);
            
            // Добавляем в новую
            regionManager_.addToRegion(object_, newRegion);
            
            // Обновляем свойство объекта
            object_->setProperty("currentRegion", newRegion);
        }
        
        // 4. Создаём команды проверки коллизий
        auto objectsInRegion = regionManager_.getObjectsInRegion(newRegion);
        std::vector<std::shared_ptr<ICommand>> collisionChecks;
        
        for (auto& other : objectsInRegion) {
            if (other != object_) {
                collisionChecks.push_back(
                    std::make_shared<CheckCollisionCommand>(object_, other)
                );
            }
        }
        
        // 5. Заменяем макрокоманду
        if (!collisionChecks.empty()) {
            collisionMacro_ = std::make_shared<MacroCommand>(collisionChecks);
        }
    }
};
```

## 6. Преимущества и недостатки

### 6.1 Преимущества паттерна CoR

| Преимущество | Описание |
|--------------|----------|
| **Ослабление связанности** | Отправитель не знает, кто обработает запрос |
| **Гибкость** | Легко добавлять/удалять обработчики |
| **Единственная ответственность** | Каждый обработчик делает одно дело |
| **Открытость/закрытость** | Новые обработчики добавляются без изменения существующих |

### 6.2 Недостатки

| Недостаток | Описание |
|------------|----------|
| **Нет гарантии обработки** | Запрос может дойти до конца цепочки без обработки |
| **Сложность отладки** | Труднее отследить путь обработки запроса |

### 6.3 Преимущества пространственного разбиения

- **O(N) вместо O(N²)** для разреженных сцен
- **Локальность** — объекты рядом проверяются вместе
- **Масштабируемость** — работает для большого числа объектов

## 7. Связанные паттерны

| Паттерн | Связь |
|---------|-------|
| **Composite** | Часто используется вместе — обработчики могут быть листьями или контейнерами |
| **Command** | Запрос можно представить как команду |
| **Decorator** | Похожая структура, но другая цель |

## 8. Применение в реальных системах

1. **Middleware в web-фреймворках** — цепочка обработчиков HTTP-запросов
2. **Event bubbling в GUI** — события поднимаются от элемента к родителям
3. **Фильтры в Java Servlet API** — `FilterChain`
4. **Обработка исключений** — `try/catch` это цепочка обработчиков исключений
5. **Физические движки** — проверка коллизий с пространственным разбиением

## 9. Заключение

Паттерн "Цепочка обязанностей" — мощный инструмент для:
- Организации гибкой обработки запросов
- Разделения ответственности между обработчиками
- Динамического изменения логики обработки

В контексте проверки коллизий паттерн позволяет:
- Эффективно организовать перебор объектов
- Гибко управлять системами окрестностей
- Легко расширять функциональность
